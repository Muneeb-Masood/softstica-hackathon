# AED Discovery & Routing — Sentosa Prototype

A planning tool that ranks nearby Automated External Defibrillators (AEDs) for a
place, date, and time you choose, explains why it picked the one it picked, and
tells you honestly when it isn't sure.

**This is not a live emergency app.** It does not know whether any AED is
physically present or working right now. It uses historical registry data
(a public government list of AED locations) and a saved map of walking
paths, and simulates what a good recommendation would look like if you were
standing at a chosen spot at a chosen time. Every screen in the app and every
API response repeats this in plain words. In a real emergency, call your
local emergency number and follow on-site instructions — do not rely on this
tool.

Built for Lane 1 ("Discovery and Routing") of an AED hackathon challenge,
using Singapore's SCDF Public Access AED dataset from data.gov.sg, scoped to
Sentosa Island for the demo.

---

## 1. What problem this solves

A dot on a map is not the same thing as an AED you can actually reach in
time. Three things can make the "closest" AED on a map the wrong real
choice:

1. **The straight line to it isn't walkable.** Water, buildings, fences, and
   one-way paths mean the closest AED by straight-line distance is often not
   the fastest one to actually walk to.
2. **It might be closed.** AED locations are inside buildings and attractions
   that have opening hours. An AED behind a locked gate at 11pm is not a
   real option at 11pm, even if it's five metres away.
3. **It might be hard to find, or the location record might be poor
   quality.** A description like "near the entrance" is far less useful in
   the field than "beside the ticket counter, Level 2, next to the lift." A
   record with a missing floor number and unparseable opening hours text
   should not be trusted as much as a complete, clearly written one.

This tool answers a single question honestly: **"If I were at this specific
place, on this specific date and time, which AED is actually the best real
choice, how confident should I be in that answer, and what's the runner-up
in case the top pick doesn't work out?"**

It is meant for people planning ahead, not people in the middle of an
emergency:

- **Venue safety planners** checking whether AED coverage at an attraction
  is actually good at a specific time of day, once real walking distance and
  opening hours are taken into account, not just what a map looks like.
- **People who maintain the AED registry** (e.g. the agency or venue
  operators), who need a concrete, reasoned list of which records are
  unreliable and specifically why, so they know what to go re-check.
- **Members of the public** planning a visit somewhere in advance, purely
  for peace of mind, not during an actual emergency.

## 2. What data this uses, and what it does not use

**Source data:** SCDF's Public Access AED list, published on data.gov.sg,
as a GeoJSON file (`AED_LOCATIONS.geojson`), covering roughly 9,000–10,000
AEDs across Singapore. Each record has:

- a unique ID
- latitude and longitude
- building name and address
- floor level (sometimes blank)
- a free-text description of exactly where inside the building the AED is
- a free-text description of opening hours

**Scope for this prototype:** the full national file is filtered down to a
bounding box around Sentosa Island (longitude 103.815–103.825, latitude
1.245–1.260), giving **66 AED records**, saved as
`backend/sentosa_aeds.geojson`. Sentosa was chosen because it is
self-contained and has a good mix of building types (hotels, attractions,
transport stations, car parks) to demonstrate the ranking logic on. Every
part of the system after this filtering step reads only this 66-record
file, never the national one.

**What this data does NOT contain, and what this tool never pretends to
have:**

- Whether any specific AED is present right now, or whether it is working
- Real foot-traffic or crowd numbers
- Real emergency call data or incident history
- Any information about people or patients

Anywhere the app shows something that sounds like crowd data (see the
"crowd simulation" feature below), it is simulated data generated by the
tool itself for demonstration purposes, and it is labelled as simulated
everywhere it appears.

## 3. How the ranking works, in plain language

For a given test location (a point on the map), date, and time, every one
of the 66 Sentosa AEDs is scored on four things, and combined into one
final number between 0 and 1. Higher is better. The four things are:

1. **How long it actually takes to walk there** (not straight-line
   distance — see below)
2. **How confident the walking-time estimate is** (some AEDs share an
   entry point on the map with other AEDs, which makes the estimate less
   precise — see below)
3. **How confident the tool is about whether the place is open at the
   chosen date and time**
4. **How trustworthy and complete the AED's registry record is** (floor
   number present, description specific enough to actually find it,
   opening-hours text written clearly)

Each of these is explained in detail below, followed by the exact formula
used to combine them.

### 3.1 Walking time, not straight-line distance

The required baseline for this kind of tool is the simplest possible
approach: measure straight-line ("as the crow flies") distance from the
test point to every AED, and rank by that. This prototype includes that
baseline (`rank_by_straight_line` in `backend/distance_ranking.py`) so it
can be directly compared against the real method — but straight-line
distance is not what actually gets used for the final ranking, because it
can be badly wrong. It ignores water, walls, fences, and the fact that
paths often bend around buildings.

The real method downloads Singapore's actual pedestrian path network for
the Sentosa area from OpenStreetMap (a free, open map database) using a
tool called `osmnx`, and finds the real shortest walking path from the test
point to each AED using standard shortest-path graph search (`networkx`,
Dijkstra's algorithm). Walking time is then:

```
walking_time_seconds = path_length_in_metres / walking_speed_m_per_s
```

The default walking speed is 1.34 metres per second (about 4.8 km/h, a
typical adult walking pace) and can be adjusted with a slider in the app
between 0.3 and 2.5 m/s to represent slower or faster walkers. There is
also a "wheelchair" mode, which removes every path segment tagged as
stairs from the map before searching for a route — so an AED that can only
be reached via stairs is correctly reported as unreachable for that mode,
rather than silently including stairs in the walking time.

**Concrete example found during testing:** at one test point on Imbiah
Road, straight-line distance says Le Meridien hotel is the closest AED
(120 metres away). But the real walkable path to Le Meridien is longer than
it looks on a straight line, and the real shortest-walking-time AED from
that point turns out to be a different one, Beach Arrival Plaza (160
seconds of walking vs. 178 seconds) — the straight-line answer would have
sent someone to the wrong, slower AED.

If there is no walkable path at all from the test point to a given AED, that
AED is marked unreachable and is excluded from the ranking rather than
being scored as if it were reachable.

**Route quality warnings.** Whenever the actual shortest walking path uses
a segment of the map tagged with something relevant, the app shows a
plain-language warning rather than silently ignoring it:

- the route includes stairs
- the route crosses a road with no marked pedestrian crossing nearby
- the route uses a path only tagged as "permissive" (tolerated, not a
  guaranteed public right of way)
- the final stretch of the route uses an estimated building entrance point
  rather than a real, surveyed doorway (see next section)

### 3.2 Why some walking-time numbers are less trustworthy than others

OpenStreetMap's pedestrian map data covers public streets and paths, but
it does not map the inside of buildings, and often does not mark every
individual building entrance. This causes a real problem: several AEDs
inside the same building can all end up mapped to the exact same single
nearest point on the street network, because that is the only point near
the building that OpenStreetMap actually knows about. When that happens,
the tool cannot really tell those AEDs apart by walking time — they all
report an identical or near-identical number, which overstates how precise
that number actually is.

Measured on the initial 66-AED Sentosa dataset: **51.5% of AEDs shared
their nearest street-network point with at least one other AED.**

**The fix — synthetic entrance points.** For every building (from
OpenStreetMap's building outline data) that has an AED within 25 metres of
it, the tool generates several evenly-spaced points around that building's
outline and adds them to the walking-path network as extra possible "doors"
into the building, roughly one every 15 metres of the building's perimeter.
These are clearly not real, surveyed doorways — they are evenly spaced
guesses around a mapped outline — so every route that ends up using one is
tagged and flagged in the app (the "estimated entrance point" warning
mentioned above), never presented as a confirmed real entrance.

This measurably reduced the problem: the share of AEDs sharing a nearest
point with another AED dropped from 51.5% to 15.2% dataset-wide. For
Universal Studios Singapore specifically, all 19 of its AEDs went from
sharing 10 points down to 19 separate points — one per AED. It did not
fully solve every case: one large building (Equarius Hotel) still only
partially separates its AEDs' walking-time estimates, and this remaining
limitation is reported honestly rather than hidden.

**The confidence number that comes out of this** is:

```
distance_confidence = 1 / (number of AEDs sharing this AED's nearest map point, including itself)
```

So an AED with a unique nearest point gets `distance_confidence = 1.0`
(fully confident). An AED sharing its point with two others gets `1/3 ≈
0.33`. This number is shown alongside every ranked result, not hidden
inside the final score.

### 3.3 Opening hours

Each AED's `OPERATING_HOURS` text (for example `"Mon - Fri 08:30-18:00;
Sat - Sun Closed"` or `"Mon - Sun 00:00-23:59"`) is parsed by a
rule-based (not AI-based) text parser. Given the text and a specific test
date and time, it returns one of three statuses and a confidence score:

| Status | Meaning |
|---|---|
| `open` | the parser matched a day/time pattern covering the test date, and the test time falls inside it |
| `closed` | the parser matched a day/time pattern covering the test date, and the test time falls outside it |
| `unknown` | the text could not be confidently matched to the test date at all |

Confidence is `1.0` if every part of the text parsed cleanly, `0.5` if only
some parts did, and `0.0` if none of it could be parsed, or if the test
date simply isn't mentioned anywhere in the text. **The parser is
deliberately built to say "unknown" rather than guess** whenever it is not
sure — this is a direct, concrete instance of the brief's requirement to
"safely abstain when accessibility cannot be established."

### 3.4 Registry trust / findability score

Independent of any specific query, every AED record gets a data-quality
score from -3 to +3, built from four rule-based checks:

| Check | Points |
|---|---|
| Floor level is filled in | +1 if present, 0 if blank |
| Description names something concrete (a kiosk, a lift, a shop name, an entrance, etc. — checked against a list of about 80 landmark words) | +1 if a concrete anchor is found |
| Description only uses vague directional words ("near", "opposite", "beside") with nothing concrete to anchor them to | −1 |
| Description is blank, or is neither clearly vague nor clearly concrete | 0 |
| Opening-hours text quality, taken from §3.3's parse confidence | +1 if confidence is 1.0, 0 if confidence is 0.5, −1 if confidence is 0.0 |
| Description contains language suggesting a process stands between arriving and reaching the AED (e.g. "approach security", "ticket required", "call ahead") | −1 if such language is found, 0 otherwise |

These add up to a total score from −3 to +3, mapped to a badge:

- **High** — total score of 3 or more (every check passed)
- **Medium** — total score of exactly 2
- **Needs Verification** — total score of 1 or less

**Important design rule:** even a single −1 anywhere caps the whole record
at "Needs Verification," no matter how good everything else about it is.
For example, a record with a perfect floor number and perfect opening
hours, but only a vague description ("near the entrance," no landmark),
still gets capped at "Needs Verification." This is deliberate: a genuinely
unfindable location, or a real access barrier, or completely unparseable
hours, is a real problem on its own — it should not get averaged away just
because other unrelated fields happen to be fine.

This access-barrier check only ever reduces confidence — it never invents
or estimates a time delay, because there is no real data on how long any
such process (e.g. checking in with security) actually takes, and making up
a number would create false certainty the tool does not actually have.

### 3.5 Combining everything into one final ranking score

For a specific test location, date, and time, each AED's final score is:

```
final_score =  0.55 × time_score
             + 0.15 × distance_confidence
             + 0.15 × hours_confidence
             + 0.15 × trust_score_normalized
```

Where:

- **`time_score`** turns walking time into a 0–1 number that drops off
  smoothly the longer the walk is:
  `time_score = e^(−walking_time_seconds / 1200)`
  (1200 seconds = 20 minutes is the "half-scale" point — a documented,
  chosen constant, not a measured real-world value. An earlier version
  used 300 seconds instead, but testing found this made short walks matter
  too little beyond about 10–15 minutes, letting a much longer walk
  outrank a much shorter one purely because of a trust-badge difference.
  Raising it to 1200 fixed that failure case while keeping the other three
  factors able to break close ties, as intended — see
  `backend/findings.md` for the full before/after numbers.)
- **`distance_confidence`** is the §3.2 value (1 ÷ number of AEDs sharing
  a map point), already between 0 and 1.
- **`hours_confidence`** is the §3.3 parse confidence, but only counted if
  the AED is actually `open` at the test time. If it is `closed` or
  `unknown`, this term is `0.0` in the score (though the app still shows
  the actual status as its own separate label — the zeroing only affects
  this one number inside the formula, not what's displayed).
- **`trust_score_normalized`** rescales the §3.4 score from its native
  −3..+3 range to 0..1: `(trust_score + 3) / 6`.

**Why walking time gets more than half the weight:** the brief treats real
walking-network distance as the primary thing being ranked on, and treats
the other three (confidence, hours, trust) as signals about how much to
trust that ranking — not separate ranking criteria of equal importance. So
walking time gets the majority weight, and the rest split the remainder
evenly. This was checked, not just assumed: across a systematic sweep of
all 657 points on the walking-path map used as candidate test locations,
the three 15%-weighted factors were still able to break close ties (1,909
tie-breaks recorded), but the largest walking-time gap any of those
tie-breaks ever overturned was capped at about 4 minutes — confirming the
weighting can't let confidence/trust alone override a walk that's many
minutes longer.

**AEDs that are excluded from the ranked list entirely**, rather than
scored with a penalty:

- any AED with `reachable = false` (no walking path exists from the test
  point at all)
- any AED that the §3.3 parser is confident is `closed` at the exact test
  date and time

Both are returned in a separate `excluded` list with a plain-language
reason, so they're visible and explained rather than silently dropped, but
they are never allowed to appear in the ranked recommendations. AEDs with
`unknown` hours status (the parser couldn't determine open/closed) are
**not** excluded — "we don't know" is a different, weaker claim than "we
know it's shut," and treating unknown the same as closed would itself be a
kind of guess. Instead, `unknown` AEDs stay in the ranked list with their
`hours_confidence` term at `0.0`, which naturally pulls their score down
without excluding them outright.

Every ranked result shows its individual sub-scores (walking time,
distance confidence, hours confidence, trust badge) next to the final
number — nothing is hidden behind one opaque score.

### 3.6 Plain-language explanations

For the top-ranked AED, and a one-line comparison for each runner-up, the
backend asks a small AI model (Google's Gemini 2.5 Flash) to turn the
already-computed sub-scores into a short, honest sentence. The model does
not do any of the ranking math itself — it only narrates numbers that were
already calculated by the rules above. It is instructed to:

- state the recommendation plainly and confidently first
- if there is a real caveat (e.g. a shared map point lowering distance
  confidence, or unparseable hours), name the specific number behind it,
  rather than a vague "please verify" hedge
- never invent a caveat when nothing is actually uncertain
- for runner-ups, explicitly name which specific number explains why it
  came second (for example: "18 seconds slower to walk to, everything else
  tied" or "actually faster, but its distance-confidence is only 0.5
  because it shares a map point with another AED")

Each explanation is generated once per unique combination of (location,
date, time, and the exact sub-scores of the top two AEDs) and cached to
disk — repeat queries reuse the cached text instead of calling the AI model
again, which keeps the tool fast and inexpensive to demo repeatedly.

### 3.7 Chat questions grounded in what's on screen

There is also a simple chat box. It only ever answers using the exact
numbers already shown on screen for the current query — it cannot invent
a new walking-time estimate, change any score, or answer questions about
things the tool has no data on (like live traffic or whether an AED's
battery is charged). If asked something it can't answer from the data on
screen, it says so rather than guessing. This is rate-limited per session
as a safeguard against runaway API usage during a demo.

## 4. Two bonus features beyond the core ranking

### 4.1 Time slider

Because opening hours and (in principle) other factors can change through
the day, the app lets you drag a slider across 24 hours for a fixed test
location and date, and see the ranking update instantly. To make this
fast, the backend computes all 24 hourly rankings in one request up front,
rather than making the frontend ask again for every tiny slider movement.
(Explanations for every single hour would mean 24 AI model calls per
query, so the tool only asks the AI model for a fresh explanation when the
actual #1-ranked AED changes between hours, up to a fixed cap per query —
any hour beyond that cap shows a generic note instead of possibly reusing
text that names the wrong AED.)

### 4.2 Crowd simulation (simulated, not real, data)

To show how a single-person ranking can hide bottlenecks across a busy
attraction, this feature lays a grid of simulated starting points across
one chosen attraction's footprint (for example, Universal Studios
Singapore) and runs the full ranking pipeline from every single grid
point. It then reports which AED comes out as the #1 pick most often
across the whole grid — a rough way of showing which AED is the
consistent best answer for an entire area, not just one exact spot.

**This uses no real foot-traffic data of any kind.** Every starting point
is a synthetic point on a grid generated by the tool itself, and this is
stated directly in the result and in the UI every time it's shown, on top
of the standing "this is a simulation" banner that's always on screen.

It also honestly reports a real limitation it can surface: for buildings
where OpenStreetMap has very little mapped interior path detail, many
grid points that are physically far apart inside the building can all end
up snapping to the same single nearest map point, making the "bottleneck"
result less meaningful for that building. The tool detects and reports
this case explicitly (`indoor_snap_degenerate` in the result) instead of
quietly presenting a falsely precise-looking answer.

### 4.3 Registry quality view

A separate view (not tied to any specific location, date, or time) lists
every Sentosa AED whose trust score (§3.4) is below "High," grouped into
two tiers — an urgent list (badge = "Needs Verification," meaning it has
at least one real −1 problem) and a lower-priority list (badge = "Medium,"
meaning it's just one field short of a perfect score, like a missing floor
number). Each entry comes with a plain-language reason pulled directly
from its own sub-scores. This is a direct, concrete answer to the brief's
request for a way to "safely abstain" and flag what needs re-checking, and
turns the registry-quality signal into a usable to-do list rather than
just an internal number.

## 5. Baseline vs. final method — what actually changed, measured

| | Baseline (required minimum) | Final method (what's actually used) |
|---|---|---|
| Distance measure | Straight-line distance | Real shortest walking-network time |
| Opening hours | Not considered | Parsed and factored in; closed AEDs excluded |
| Record quality | Not considered | Trust score factored in |
| Map-precision uncertainty | Not considered | Shared-map-point penalty factored in |

**How often they actually disagree:** across 200 sampled test points, the
straight-line baseline and the final method picked a *different* #1 AED
**51.5% of the time**. In other words, more than half the time, the
"obviously closest" AED on a plain map is not the AED this tool would
actually recommend once real walkability, hours, and record quality are
taken into account — directly demonstrating why the brief calls the
straight-line baseline insufficient on its own.

**Safety check:** across the same 200 test points, zero excluded
(closed or unreachable) AEDs ever leaked into the ranked list, and the
count of ranked plus excluded AEDs always matched the total of 66 — no
AED was ever silently dropped.

**Speed:** the core ranking calculation itself takes about 63ms on average
(114ms at the 95th percentile) with no AI model call involved. A fresh
API request that also needs a new AI-generated explanation (i.e. a query
never seen before) takes a few seconds, almost entirely due to that one
AI model call; a repeated query that reuses a cached explanation responds
in about 100ms.

**Typical vs. worst-case walking time to the top pick:** across the 200
sampled test points, the recommended AED's real walking time averaged
about 2.4 minutes, but the 95th-percentile case was about 8.6 minutes —
showing that a plain average would hide a real minority of locations on
Sentosa where even the best available AED is a considerably longer walk,
which is itself a useful, honest finding about where AED coverage could be
improved.

Full numbers, methodology, and additional metrics are in
[`DELIVERABLES.md`](DELIVERABLES.md).

## 6. Safety and privacy, in plain terms

- This tool never claims to know whether an AED physically exists,
  is present, or is working, right now. It only works from a historical
  registry list.
- Every opening-hours result is a best-effort estimate from parsing text,
  never a live check.
- Every confidence or trust number shown anywhere in the app is clearly a
  model estimate about data quality — never a claim about the real,
  physical world.
- AEDs that are closed or unreachable are removed from the recommendation
  list entirely, rather than risk being mistaken for a real option.
- Anything built from simulated data (the crowd-simulation feature) is
  labelled as simulated everywhere it's shown, never presented as real
  foot-traffic or incident data.
- The dataset contains no personal information of any kind — only public
  AED equipment locations and registry text.
- No user's location, search history, or chat messages are saved to disk.
  Chat rate-limit tracking is kept only in memory while the server is
  running and is lost on restart.
- The AI model API key is read only from a local, untracked configuration
  file, is never logged or written to any saved file, and only the
  specific numbers needed for one explanation are ever sent to the AI
  model — never a full data dump.
- A visible reminder that this is a simulation/planning tool, not live
  emergency guidance, is shown on every screen of the app and included in
  every backend response.

## 8. How to set it up and run it yourself

This runs entirely on your own computer. Nothing needs to be deployed
anywhere for the demo.

### 8.1 What you need first

- **Python 3.12** (or close to it)
- **Node.js** (for the frontend; comes with `npm`)
- A **free Google Gemini API key** — this is only used for the two
  plain-language explanation features (section 3.6 and 3.7). The core
  ranking math (walking time, hours parsing, trust score, and the final
  ranking formula) runs completely without it, using no API key at all.
  You can get a free key at Google's AI Studio site.

### 8.2 Backend setup

Open a terminal in the `backend` folder and run, one line at a time:

```powershell
cd backend
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
```

Then open the new `.env` file and put your Gemini API key in it:

```
GEMINI_API_KEY=your-actual-key-here
```

Then start the backend server:

```powershell
uvicorn main:app --reload
```

To check it's working, open `http://localhost:8000/health` in a browser.
It should show `"data_loaded": true` and a `startup_time_s` value of a few
hundred milliseconds — this confirms the AED list and the cached walking
map both loaded from the already-saved files, with no live downloading
happening at startup.

### 8.3 Frontend setup

Open a **second** terminal, in the `frontend` folder:

```powershell
cd frontend
npm install
npm run dev
```

This starts the frontend at `http://localhost:5173`. Open that address in
a browser. It automatically talks to the backend at `http://localhost:8000`,
so make sure the backend from step 8.2 is still running.

### 8.4 Using it

1. Click anywhere on the Sentosa map to set a test location (or type an
   address/search term, if supported in the current UI).
2. Set a date and time.
3. Optionally adjust the mobility mode (walking vs. wheelchair) and walking
   pace.
4. The ranked list of AEDs appears, each with its walking time, confidence
   sub-scores, trust badge, and a plain-language explanation.
5. Drag the time slider to see how the ranking would change at different
   times of day for the same location.
6. Try the crowd-simulation panel to see a simulated bottleneck AED across
   an entire attraction.
7. Check the registry-quality list to see which AED records in the dataset
   most need to be re-surveyed, and why.

### 8.5 Regenerating the underlying data from scratch (only needed if you want to rebuild it)

The filtered dataset and the walking-path map are already generated and
saved in the `backend` folder, so this step is **not required** for a
normal run — the backend loads the saved files and never re-downloads
anything live. If you do want to regenerate everything from the original
national dataset:

1. Filter `AED_LOCATIONS.geojson` down to the Sentosa bounding box
   (longitude 103.815 to 103.825, latitude 1.245 to 1.260) to produce
   `sentosa_aeds.geojson`.
2. Run `build_building_footprints.py` to download building outlines near
   the Sentosa AEDs from OpenStreetMap.
3. Run `entrance_augmentation.py` to build the final walking-path map,
   combining the raw OpenStreetMap walking network with the synthetic
   building-entrance points, saving it as
   `sentosa_walk_graph_augmented.graphml`.

### 8.6 Running the automated tests

With the backend virtual environment activated:

```powershell
cd backend
pytest
```

This runs the automated checks for the opening-hours parser, the trust
score, the crowd simulation, and the time-slider explanation logic.

## 9. Known limitations, stated honestly

- OpenStreetMap's walking-path data does not map building interiors, so
  even after adding synthetic entrance points, some large buildings (for
  example, Equarius Hotel) still cannot fully separate the walking-time
  estimate for every individual AED inside them. This is reported, not
  hidden, whenever it applies.
- The synthetic entrance points are evenly spaced guesses around a
  building's mapped outline, not real surveyed doorways. Any route using
  one is flagged as such.
- Walking speed is a constant (adjustable by the user, but not
  automatically inferred), because OpenStreetMap does not reliably provide
  a real walking speed for each individual path segment in this area.
- Almost all AEDs in the Sentosa sample used for this demo are open 24/7,
  so the "closed" and "opening-hours confidence" logic is verified by
  direct automated testing and by deliberately constructed examples, more
  than by naturally occurring closed AEDs in this specific small dataset.
- This tool has not been deployed anywhere public; it is designed to be
  run locally for the demo.
